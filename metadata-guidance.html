Purpose of the Developer Reuse Metadata Profile

The purpose of this metadata profile is to ensure that AI models can be understood, evaluated and reused by other developers, organisations or decision-makers. The profile aims to make models discoverable, transparent and technically interpretable.

The metadata must enable a technically competent reader to:

  • Understand what problem the model solves
  • Understand what data the model expects and produces
  • Assess its readiness and governance status
  • Evaluate technical and legal reuse conditions
  • Locate additional documentation or contact information

Descriptions must be clear, factual, technically precise and free from marketing language. If information is unavailable, this must be stated explicitly (e.g. “Unknown” or “N/A”).

1. Model Name

Purpose:
Provide a clear and descriptive identifier for the model.

What to include:

  • A concise, human-readable name
  • The functional domain (if relevant)
  • The data source or context (if relevant)

The name should enable catalogue users to immediately recognise the model’s purpose.

Example: Building detection (Sentinel-2)

2. Organisation

Purpose:
Identify the accountable organisation in the catalogue context.

What to include:

  • The official name of the organisation
  • The organisation responsible for ownership, governance or maintenance

This field clarifies responsibility and governance context.

Example: Lantmäteriet

3. Model Status

Purpose:
Indicate the lifecycle stage and operational readiness of the model.

The status reflects governance maturity and expected stability. Use a controlled vocabulary and apply it consistently.

  • Concept
  • Experimental
  • Validated
  • Production-ready
  • In production
  • Deprecated

If the model is no longer maintained, this must be clearly stated.

Example: Production-ready

4. AI Task

Purpose:
Describe the functional task the model performs.

Use recognised AI terminology and avoid vague descriptions.

Examples of recognised task types:

  • Image classification
  • Semantic segmentation
  • Object detection
  • Change detection
  • Super-resolution
  • Document understanding

The description should clarify the problem domain and the output semantics.

5. Input Specification

Purpose:
Describe the required input data format and constraints necessary for correct model operation.

What to include:

  • Data type and format (e.g. GeoTIFF, PDF, JSON)
  • Resolution or scale (if relevant)
  • Schema or structure
  • Coordinate reference system (if spatial)
  • Preprocessing assumptions
  • Any critical constraints

The description must enable another developer to prepare compatible input data.

6. Output Specification

Purpose:
Describe the structure and meaning of the model’s output.

What to include:

  • Output format
  • Semantic meaning of outputs
  • Class schema (if classification/segmentation)
  • Spatial properties (if geospatial)
  • Confidence scores or uncertainty measures (if available)

The output description must allow integration into downstream systems.

7. Architecture

Purpose:
Provide high-level information about the model family.

Do not include parameter counts or internal technical details unless necessary. Provide a general architectural description only.

Example: U-Net convolutional neural network

8. Training Data Origin

Purpose:
Clarify the provenance and characteristics of the training data.

What to include:

  • Dataset name
  • Geographic or thematic scope
  • Time period
  • Public availability (if applicable)
  • Known limitations or biases (if relevant)

This field supports transparency, reproducibility and responsible reuse.

9. Primary Performance Metric

Purpose:
Provide a headline metric that indicates model performance.

Include:

  • The metric name (e.g. Accuracy, F1-score, IoU)
  • The value
  • Minimal context (e.g. validation dataset)

Only one primary metric should be listed to ensure clarity.

10. License

Purpose:
Specify the legal conditions governing reuse.

Provide the official license name. If reuse is restricted, this must be stated clearly.

11. Access Link

Purpose:
Provide a stable reference for obtaining the model or documentation.

If the model is not publicly available, write “N/A”.

12. More Information

Provide supplementary material that supports responsible reuse:

  • Documentation
  • Publications
  • API documentation
  • Issue tracker
  • Contact information

Final Quality Checklist

A metadata record is considered complete if a technically competent developer can:

  • Understand the model’s purpose and task
  • Prepare compatible input data
  • Interpret and integrate the output
  • Assess training data origin and performance
  • Understand governance and licensing conditions
  • Identify where to seek additional information

If these conditions are met, the record fulfils the objective of the Developer Reuse Metadata Profile.
